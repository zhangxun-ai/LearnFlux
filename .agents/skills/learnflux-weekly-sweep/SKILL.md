# 每周代码大扫除

由用户按需手动发起，默认只读。无需设置定时任务。

按用户可观察的功能和维护成本排序。每条建议都要有调用、数据或运行证据。用户明确要求实施时，按已确认的发现做局部修复。提交、发布、外部写入和删除既有数据各自遵循项目授权。

## 定范围

- 一次只处理用户选定的一个仓库。读适用的 `AGENTS.md`，用 `git status --short` 记录现有改动。LearnFlux 的检查入口见[项目验证指引](references/learnflux.md)。
- 用户给出的提交范围优先。否则使用该仓库和分支上一次**完整扫完**的结束提交作基线，默认检查本地默认分支的最新提交。首次无基线时，取该分支最近七天的第一父链提交，以最早一条的父提交为基线。找不到默认分支时，说明当前使用的分支。
- 把基线和结束点解析为固定 SHA。用 `git merge-base --is-ancestor` 验证顺序，用 `git log --first-parent <base>..<tip>` 列出合入，再看 `git diff <base> <tip>`。上次基线不可用或历史被改写时，报告范围缺口并保留原记录。两端相同就报告无新增改动。
- 从已提交快照取证。追踪受影响的旧调用方、配置和文档时，也要标明依据来自哪个提交。复查当前工作区的修复时，另列未提交改动和相关测试的结果。

## 找问题

按用户流程归组。先查看有行为变化的入口和对应回归用例，再追查同一流程的其他入口。时间有限时优先查能产生数据写入、权限变化或重复任务的流程，并记录实际覆盖的分组。

1. **功能与数据。** 用代表性输入重现，或从入口追到状态、持久化与返回值。跨入口的同一规则要比较实际结果。涉及重试时检查原操作是否已经发生、谁能触发新操作、会产生几次任务或外部写入。
2. **过度防御与重复。** 找出该分支防的具体情况，核对接口定义、生产调用方、测试替身和历史数据。内部接口已经保证的条件，可以直接使用该接口。边界处的兼容、权限、并发、失败恢复和结果不明的防重，要用现有合同或可复现行为判断。证据不足的候选列为待核对。
3. **退役与文档。** 沿停用的字段、路由或配置名查代码、示例和测试，再从 README、文档索引或实际使用入口核对可达的现行页面。按读者看到的用途区分现行说明和历史记录。已有兼容层时说明它仍保护哪类旧调用或数据。

## 修复与验证

获准修复时，先处理会影响用户的缺陷，再简化已证实的重复逻辑。每次围绕一个行为做最小改动。

运行检查前，核对目标版本的测试收集、模块导入和测试本身都使用隔离配置与数据。历史快照尤其需要核对测试入口。环境无法隔离时，使用源码追踪或独立的最小复现，并如实说明证据类型。

行为有变化时复现旧问题并核对修复后结果，纯简化则核对输出、错误和副作用。区分测试替身、真实数据读回与真实写入，分别报告证据。

## 输出

报告仓库、分支、起止 SHA 和结论。发现按「功能缺陷」「可简化」「退役残留」归类，每条给出触发条件、影响、定位、证据和建议验证。保留理由只列容易被误删的保护。复查时逐项标记已验证、仍存在或待验证。

完整扫描后，把本次结束 SHA 作为该仓库和分支的下轮起点。抽查或扫描中断时写清覆盖范围，保留上次起点。修复是否合入、是否已验证，与扫描起点分别记录。
